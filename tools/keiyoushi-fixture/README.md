# Keiyoushi smoke fixtures (K6)

Two canned, fully offline Keiyoushi-format extension APKs +
their sources, used by the instrumented player test
(`app/src/androidTest/java/app/xreader/data/extension/player/KeiyoushiFixtureLoadTest.kt`).

| Fixture | Package | Shape | Proves |
|---|---|---|---|
| `fixture-panels.apk` | `eu.kanade.tachiyomi.extension.en.fixturepanels` | One `HttpSource` + `ConfigurableSource` (Asura's shape) | Reader metadata, class loading, the K4 adapter end-to-end (catalogue → details → TRUE chapter numbers → pages with the source's own image-url resolution + the K6 Referer stamp → page bytes), the K5 preference host building + editing a real screen |
| `fixture-factory.apk` | `eu.kanade.tachiyomi.extension.en.fixturefactory` | A `SourceFactory` making two sources (MangaDex's shape) | Factory instantiation + multi-source registration |

## Why a test key

The fixtures are signed with a LOCAL TEST KEY
(`fixture-test.jks`, generated by the build script; cert
SHA-256 `eb7cba4c…72c8` at first generation). That is the
point: they must NOT carry the Keiyoushi signing key, so the
manager's verified install path refuses them — the
instrumented test pins that refusal, and loads the fixtures
through the loader directly (the loader itself does not
verify signatures; the manager does, before the loader ever
runs). The full manager path with real bytes is proven by
the device smoke checklist against the live repo.

## Build

Not a Gradle module, on purpose: nothing here can break the
app's gate. Run `build-fixtures.sh` with the env vars its
header documents (embeddable Kotlin compiler, a `:mihon-api`
classes jar, the fixture's compile peers). Outputs land in
`app/src/androidTest/assets/`.

Sandbox note (2026-11-01): the fixture compile was verified
in the K6 harness with the real `:mihon-api` sources and a
signature-faithful androidx.preference stub overlay, because
this VM's Gradle cache holds no preference AAR. In the gate
environment the real AAR's `classes.jar` goes in `EXTRA_CP`.

## Honest bounds

- The instrumented test cannot run in this sandbox (no
  emulator; Gradle is the gate's job). It is compile-shaped
  against the same APIs the K4/K5 JVM tests exercise, and is
  prepared for the gate (compile step) + a device run.
- The `.apk` outputs and the `.jks` are binary build
  artefacts: they live in the local tree and do not travel
  through the text-only snapshot push. Regenerate anywhere
  with the script.
